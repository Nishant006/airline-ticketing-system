# ATS-1: design decisions

Corrected 2026-10-19 against the authoritative brief and user decisions; stateless
scaling scope clarified 2026-10-20.
This replaces the earlier conflicting draft. Historical decisions in the execution log
are not current implementation instructions. See [spec.md](spec.md) for the contract.

| Decision | Choice | Alternatives and consequences |
|---|---|---|
| Deployment | User-accepted single stateless Spring Boot backend, PostgreSQL primary | On 2026-10-20 the user accepted a stateless backend and delegated scaling judgment without a fixed peak request-rate requirement. Multiple app instances share database invariants; reviewer default is one. Microservices and distributed transactions are not required. |
| On-demand scaling | Add identical replicas behind a readiness-aware load balancer; retain a bounded database connection budget | No sticky sessions or JVM-local seat ownership. Existing Compose supports manual replica changes; production load balancing/autoscaling is a deployment concern, not implemented cloud infrastructure. Maximum simultaneous replicas, including rollout surge, must fit PostgreSQL capacity. More app replicas do not remove database or hot-seat contention. |
| Persistence | User-confirmed Spring Data JPA, Flyway and Spring transactions | Standard repositories replace custom persistence ports/adapters. JPQL handles aggregate projections; only the PostgreSQL instance upsert needs native SQL. JPA does not replace the database's active-seat invariant. Flyway owns DDL; Hibernate validates it. |
| Code organization | User-selected package-by-layer, service interfaces plus `service.impl`, immutable `model` commands/results, flat Spring Data `repository` | This supersedes both feature grouping and the intermediate strict repository-port/JPA-adapter split. Separate transport records per use case; no entity API responses or cross-service entity exchange. Implementations intentionally know JPA: conventional layered design, not a persistence-independent core. No catch-all DTO, `var`, or pass-through repository wrappers. |
| Public contracts | Narrow use-case interfaces; transport mapping at controllers and persistence mapping inside service implementations | Interfaces express actual operations rather than generic CRUD. Application models have no JSON/JPA/Spring dependencies. Search projects `FlightAvailability`, not an API DTO. Service interfaces improve dependency boundaries/testability, not throughput by themselves. |
| ORM performance | Application-model search projection, explicit aircraft fetch graph, OSIV disabled | Reads do not hydrate every schedule/seat or trigger lazy N+1 access. Shared immutable `SeatLayout` avoids duplicating aircraft rules. Existing IDENTITY keys are retained: ordered seat saves are individual inserts, not a claimed JDBC batch. Measure before changing ID generation or adding caching. |
| Generation | Hybrid: project flights from schedules; persist instances lazily | Full materialization is allowed but needs rolling-horizon maintenance. Dynamic-only storage is viable but complicates booking references. Hybrid needs read paths that tolerate missing instance rows. |
| Seat ownership | Derived layout and partial unique active-allocation index | Per-flight inventory rows and parent-flight optimistic/pessimistic locking are valid alternatives, not inherently wrong. The chosen index prevents competing seat ownership without serializing every booking on a flight counter. |
| Cancellation | Atomic status change and seat release | User selected repeat/departed cancellation as 409. This is not a hiring requirement. Historical allocations are retained, while the partial index allows reuse after release. |
| Time | UTC times/dates and injected UTC Clock; 365-date half-open horizon | Airport-local conversion is excluded. No approximate departure instants. The exact boundary is documented and tested, including leap years. |
| Public identity | Flight number plus date; UUID booking reference | One immutable schedule per number is a documented simplifying assumption. UUID is expressly allowed, so no custom PNR alphabet/retry is needed. |
| API scope | Five required operations only | Listing schedules, retrieving bookings and idempotency headers are not required and are deferred. UUID references alone do not make POST retries idempotent; a lost response remains a documented limitation. |
| Availability | Count active allocations; live seat-map query | No inventory counter or mutable cache. Reads are snapshots and can become stale before a later booking, whose conflict response is authoritative. |
| Transactions | READ COMMITTED; separate sequential materialization and booking transactions; coordinator uses NEVER | Ambient transactions are rejected before persistence, rather than silently breaking rollback-before-conflict-read semantics. Nested REQUIRES_NEW can require a second connection per request. Instance insert uses DO NOTHING then a separate SELECT; normal existing-instance lookup does not issue a no-op UPDATE. |
| Read protection | User-approved dedicated read pool: max 5, acquisition 250 ms, SQL 500 ms, lock 250 ms; write pool retains max 10/acquisition 20 s | Spring lazy read-only routing uses the same primary and honors Boot/Testcontainers connection details. Saturated reads return explicit 503 without consuming write connections. Total default budget is 15 per replica/45 for three. Limits bound DB waits, not HTTP queueing/network/initial connection establishment; overload is not a successful empty search. |
| HTTP preflight | JSON response negotiation before invocation; strict HH:mm clocks | Prevents committing a write then returning 406, and prevents 24:00 silently becoming 00:00. Cancellation still accepts an empty body without a Content-Type. |
| Errors | RFC 9457 plus stable codes; named-constraint discrimination | Seat conflicts are 409 only for the actual seat index, not every integrity violation. Failed transactions finish rollback before further reads. Spring's SQL translator also classifies Hibernate-wrapped PostgreSQL shutdown errors as 503; unclassified ORM failures remain 500. Writes with unknown outcomes are not blindly retryable. |
| Verification | JUnit, ArchUnit and real PostgreSQL/Testcontainers | Tests verify the production database mechanisms. Query-count checks and EXPLAIN are diagnostics, not substitutes for measuring HTTP latency or instructions to force one planner choice. |
| Local latency acceptance | Every measured warm read-only search and every search in the existing 16-client mixed baseline must return 200 in under one second | This is an engineering gate chosen under the user's delegated judgment, not a peak-RPS contract or an interviewer-specified percentile. Existing 64/192-client phases remain exploratory stress: 503s are explicit failures to serve search, successful-response latency is reported separately, and an all-shed phase must fail. Booking ownership/correctness remain mandatory in every phase. |
| Libraries | JDK records/UUID/time; Lombok; Spring Data JPA, MVC, Jakarta/Hibernate Validation | No custom connection manager, JSON parser, validation framework or UUID generator. Add Apache utilities only for a real missing operation, not to wrap a JDK equivalent. |
| Documentation | Small maintained HLD/LLD/README plus executable migrations | Do not repeat speculative grade weights, unsupported latency claims or historical audit narratives as architecture. Audit after every five completed todos and fix findings before continuing. |
